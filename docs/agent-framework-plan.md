# Agent 框架完善计划

状态：计划，尚未实施。日期：2026-09-11。

后续范围调整：用户选择先收尾 YC-Code，再转 Shopping。本文保留为原始扩展计划，不再是当前待执行清单；0.6 实际实现及边界以 README 和 closeout.md 为准。

## 目标与范围

先交付可以演示真实仓库阅读、问题定位、代码修改、测试反馈修复和会话续接的 Python Single Code Agent，并以可复现证据支持面试讲解。沿用一个 OpenAI-compatible Provider，当前使用 DeepSeek。后训练阶段另行启动。

第一版不加入 Plan/Do、多 Provider Adapter、Multi-Agent、MCP、自动长期用户画像或 RL Trainer。保留已有接口，按实际职责增添少量模块，不整体重写。

## 当前事实

- core.py 有模型/工具循环、步数限制和 Provider 临时错误重试；上下文仅按 content 字符数截短长工具结果，没有结构化摘要、完整请求预算或紧急压缩。
- tools.py 有文件工具、BM25 检索、路径检查、写入白名单和受限命令；命令输出目前先全部缓冲再截断，不能视为执行期内存上限。
- state.py 保存会话和 FIFO 任务状态；尚不保证中途故障后的安全恢复。
- repo_eval.py 在临时副本执行并注入 verifier；尚未实现 Docker 后端及干净副本应用最终 patch 复验。
- benchmark.py 的 tool_retry 会收到隐藏测试输出；应改为仅接收公开开发测试反馈，最终隐藏评分独立执行。既有结果不能当作无隐藏反馈的标准评测。
- JSONL 和偏好导出可复用，但未记录每次实际请求的完整上下文、配置版本和截断决策，也不等于已经接通训练。

## M0：固定基线（0.5天）

保存当前版本、测试结果、四个多文件任务的已有结果和现有功能清单。增加固定离线脚本模型，用于故障注入。时间为专注开发估算，不含长时间 API、镜像下载和学习。

验收：离线 demo 和单元测试可运行；区分参考修复通过率、自建任务模型结果与真实 issue 结果。

## M1：上下文与日志产物（1.5–2天）

- 保留 system、原始任务和近期完整 assistant/tool 消息组。
- 将完整工具结果存为运行目录中的 artifact，模型收到有长度限制的摘要与 artifact ID；支持按行读取，禁止越界。
- 程序维护已读取/修改文件、开发测试状态、预算；根因假设由模型提供且明确标为假设。
- 预算覆盖消息、工具定义及 arguments/reasoning 等实际发送字段，并预留输出空间。API 下无本地精确 tokenizer 时标记估算，另存服务端真实 usage。
- 阈值触发结构化历史摘要；摘要失败使用确定性压缩；处理上下文超限时至多一次受控压缩重试。
- 记录实际请求、摘要来源事件及压缩前后估算；禁止记录凭证。

验收：长日志可回读；压缩后任务和工具配对保留；超限有明确终止原因；相同输入可以重建实际请求；离线测试覆盖摘要失败。

## M2：工具与运行控制（1–1.5天）

- 统一工具结果字段：成功状态、退出码、超时、截断、artifact ID、耗时。
- 强化工具参数验证，保留精确编辑与路径检查；运行时限制输出采集，超时终止整个子进程组。
- 增加整次运行时间和调用预算、重复无进展检测、明确结束原因。
- 测试通过由测试工具报告；模型结束只意味着提交，不自动等同成功。API 重试与任务修复重试分别记录。
- 保留部分失败轨迹和 usage；不对可能已执行的写操作盲目重试。

验收：故意触发非法参数、编辑不匹配、超时、巨大输出和重复操作，均能恢复或有界停止，记录完整。

## M3：可用 CLI 与安全续接（1–1.5天）

- 提供连续交互、工具执行进度、会话列表/续接和最终 diff 摘要。
- 每个完整步骤持久化；绑定 workspace 与配置，恢复前核对文件变更。
- 对中断时可能已经执行的操作保留不确定状态，先检查结果，再决定是否执行。
- 一个 Provider 上增加可选流式文本与工具参数组装；流未完整结束前不执行工具。流式工作可在核心续接验收后交付。

验收：先修改再追问不丢上下文；中途退出后能继续；恢复不会重复执行写入；流式中断不执行半个工具调用。

## M4：容器执行与真实仓库（1.5–2天）

- Docker 中执行 Agent 生成或修改的代码，宿主 API key 不传入任务容器；限制资源、挂载、超时及网络。
- 每次运行独立初始仓库，捕获最终 patch；在第二个干净副本应用 patch 并运行最终 verifier。
- 区分开发测试和隐藏评分：隐藏反馈既不进入循环，也不进入摘要或检索。
- 自建任务用于工程回归；先打通一个公开真实 issue/SWE-bench 实例，再冻结可运行的小样本清单。对平台不兼容单独记录，不悄悄删除失败样本。
- 本机先并发1；Docker约10GB仅为16GB主机上的尝试配置，是否足够由构建和测试日志判断。

验收：原仓库不变，两次任务互不污染，隐藏测试不可读，patch在干净环境可复验；失败分类有日志。

## M5：检索验证与固定评测（1–2天）

- 保留 BM25，验证行号引用、忽略目录、修改后的索引失效和搜索结果上限。
- 固定20个自建任务作回归，加5–10个可运行的公开真实issue作外部证据；资源不足先报告1个贯通结果。
- 在相同任务、模型、公开信息、上下文及预算配置下比较 Direct、Tool、Tool+开发测试反馈；独立比较 BM25开/关。先检查已有Tool是否已经使用测试反馈，保证组间行为可区分。
- Direct使用固定且不含人工答案的上下文选择方式；如果另做oracle定位对照，单独命名。
- 预算允许每题每组2–3次；明确总运行数、失败数及基础设施错误，不以少量成功案例概括整体。
- 输出完成率、回归率、Token、耗时、调用数和失败分类。性能提升以实际结果为准。

验收：产出配置、原始轨迹、patch、测试日志和汇总；至少可讲一个成功修复与一个失败案例。

## 面试与后续边界

每完成一个里程碑，准备三项内容：现场演示、一次设计取舍、一条故障证据。M1–M5达到验收后再更新简历，功能与结果逐条对应产物。

学习主题：Agent Loop与Workflow、工具Schema、Context与Memory区别、压缩信息损失、BM25与向量检索、命令隔离、幂等和恢复、评测泄漏、API成本与失败分类。没有实现MCP/Multi-Agent也应理解其协议/协作作用及适用边界，不宣称实现。

RL阶段只在框架稳定后启动。当前保存实际模型输入、动作、工具观察、最终评分、任务/模型/配置版本和终止原因。不要把隐藏测试作为在线停止信号。未来训练再接tokenizer/chat template、策略版本、模型生成token mask与logprob；环境观察不参与模型生成loss。现有episode JSONL和组内advantage不是开箱即用的GRPO训练数据。DeepSeek轨迹可评估为离线蒸馏数据来源，Qwen在线RL需要由相应策略采样。

## 排期

按约7–11个专注开发日规划；每日另留45–60分钟阅读本日代码和复述设计。镜像/平台故障单独排期。前三天优先完成M0–M2，达到上下文管理、错误恢复和有界执行这一可演示增量，再推进会话、容器与真实评测。
